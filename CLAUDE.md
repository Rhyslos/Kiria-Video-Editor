# CLAUDE.md

A fast, light, native video editor written in Rust. A hobby project, open source under GPL-3.0-or-later. Windows first, then Linux.

## Start here

1. Open [docs/build-plan.md](docs/build-plan.md). Find the first phase whose status is not "Gate passed" and take its first unticked step. A gate marked *waiting for the owner* doesn't hold work back: carry on with the next phase.
2. Read the `README.md` of every folder you will touch before writing code.
3. Finish the step (definition of done below), tick it in `docs/build-plan.md`, and update any README or this file that the change makes out of date, all in the same commit.

[docs/project-plan.md](docs/project-plan.md) says *what* the app is; [docs/build-plan.md](docs/build-plan.md) says *how* and *in what order*. If work would contradict the project plan, update the plan first and say so.

## How we work together

- **Chores happen directly:** fixing CI, dependency and tooling updates, documentation, merging finished pull requests. Commit to `main` (or merge) without asking.
- **Features come as pull requests, one feature each.** The description says what the feature does, how to try it in the app step by step, and what is not done yet. Every pull request builds a test installer (the Release workflow's `windows` artifact). The owner may ask to merge first and test through the update: every push to `main` publishes an automatic beta that installed beta copies install by themselves. Merged pull requests keep their test steps. The pull requests double as a guided tour of the app.
- **Releases:** when asked to release, bump the version and `CHANGELOG.md` (a small pull request or a direct commit), then start the Release workflow with the new tag. The workflow publishes on its own once everything passes.

## Working rules

1. **Uniform controls.** A tool behaves the same and uses the same shortcut on every page. Shared parts (playhead, edit needle, region, timeline labels, transport, the shortcut table) are built once in `crates/ui-kit` and reused, never re-implemented per page.
2. **One feel across pages.** Switching pages feels like moving around one app.
3. **Shared visuals stay put.** Top bar, page tabs (centred over the viewport), panel widths and theme tokens come from `crates/ui-kit` only.
4. **No name-dropping.** Code, comments, docs, commit messages and interface text never name other video editors or the companies that make them, for example to say where a feature comes from. Describe the feature instead. Naming the platforms and tools the app runs on or is built with (the update host, graphics interfaces, graphics card makers, FFmpeg, the operating system) is fine.
5. **Documented folders.** Every crate and every folder with more than a couple of files has a `README.md`. This file is the map. Both are updated in the same commit as the code they describe.
6. **Readable, clean, stable code.** Small modules, clear names, consistent patterns. No `unsafe` outside the FFmpeg and GPU wrappers (`crates/media`, `crates/video-device`, `crates/graphics/src/vulkan_device.rs`) and the operating-system calls (`crates/os`), each block with its reason. No `unwrap()` or `expect()` outside tests: return an explained error.
7. **Research and compare big systems.** For playback, caching, the timeline widget, rendering, the audio engine, background removal, auto white balance and the highlight finder: write a note in `docs/research/`, prototype two or three approaches in `spikes/`, measure them on the same clips, then build the winner properly.
8. **One name, one place.** The app's name and identifiers live only in `crates/brand`. A test fails if the name is typed in any other Rust file; read `brand::APP_NAME` instead.

## Definition of done

- `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` pass.
- New behaviour has tests.
- Errors are `diag::AppError` (what, why, fix, optional one-click fix), returned as `diag::Result<T>`; wrap other errors with `.or_explain(...)`. Never a bare string.
- Nothing slower than about 2 ms runs on the interface thread.
- READMEs, this file and `docs/build-plan.md` are current.

## Layout

```text
Cargo.toml           workspace, shared versions and lint rules
rust-toolchain.toml  pinned Rust version
deny.toml            dependency licence, advisory and duplicate-version checks (cargo-deny)
crates/              the workspace crates; see crates/README.md for the table
docs/                project plan, build plan, research notes, decisions, the user guide (docs/user-guide/)
spikes/              throwaway prototypes (not built)
tests/               cross-crate tests
test-media/          shared test recordings (only the manifest is in git)
xtask/               chores: `cargo xtask <ffmpeg | check-media | brand | beta-version | keygen | manifest | sign | verify | icons>`
packaging/           installers: Windows (Inno Setup), Linux (AppImage), icons, FFmpeg pin
.github/workflows/   CI on Windows, clippy alone on Linux (Linux is paused, see below); release.yml builds, tests, signs and publishes releases; spike-*.yml build spike programs to run by hand
RELEASING.md         how to make a release; CHANGELOG.md what each release changed
```

Binaries: `cargo run -p app` (the editor, binary `editor`) and `cargo run -p launcher`.

To see a window without a screen (Linux): `xvfb-run -a -s "-screen 0 1600x1000x24" target/debug/editor --screenshot out.png`, or `target/debug/launcher --demo 14 --screenshot out.png` for the project browser with sample projects. CI also runs `--smoke-test` for both.

**Linux is paused in CI and in releases** (November 2026): only Windows is built, tested and published; on Linux CI only runs clippy on the whole workspace (the `linux-lint` job), so the code keeps building there. The Linux steps are still in the workflows; each has a comment saying how to turn it back on. Until then nothing in CI runs `--responsiveness-test` or takes screenshots, so run both by hand with the commands above before merging interface work, and keep the code building on Linux.

## Commands

```sh
cargo xtask ffmpeg      # once: fetches the pinned FFmpeg build into .ffmpeg/ (needed to build)
cargo build --workspace
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all
cargo xtask check-media
```

Building needs libclang (for the FFmpeg bindings); on Windows set `LIBCLANG_PATH` if it isn't found. `.cargo/config.toml` points the build at `.ffmpeg/sdk`. On Windows, run `cargo xtask ffmpeg` again after `cargo clean`: it copies the DLLs beside the programs.

`rust-toolchain.toml` pins the Rust version, so rustup downloads it on first use. Offline, override with `RUSTUP_TOOLCHAIN=stable` for local checks; CI always uses the pinned version.

## Decisions so far

- Time is stored as exact fractions (frames over rate), never floats.
- The project file is versioned from its first commit; every format change gets a migration and a stored sample. Since format 18 (templates 2) values that are their default are left out of the file (`project::defaults`), so a default of a saved type is part of the format and changes only with a new version whose migration writes the old value in.
- How a project is looked at (track heights, the video/audio divider) is view state, not an edit: it lives in `<project file>.view` beside the project, never in the project file, and makes no undo step.
- Ways of looking at the timeline that are ways of working rather than about one project (the rough cut view, compact tracks, the divider between video and audio taken away, what a click on the timeline moves, zooming to the playhead, volume knobs or sliders and the detailed knob or no volume in the headers, nothing drawn over the picture) are settings, the same for every project; they never change the heights or the divider's place kept in the `.view` file (the selected clip's track opening up for the detailed knob is drawn taller only while it lasts).
- A clip's keyframes are kept in its file's time (source time), not the timeline's, so they stay on the picture through moves, trims and speed changes; values between keyframes are worked out in whole numbers so preview and export agree exactly.
- A clip's speed ramp (speed keyframes) is kept in timeline time from the clip's start, unlike look keyframes, because a ramp is about the timeline; where the clip is in its file is the ramp added up in whole numbers, exactly to the flick (1/705 600 000 s), so preview and export agree and steady stretches land exactly on recorded frames. Setting a ramp keeps the part of the file a clip plays; its length follows, to the nearest frame.
- A project has several timelines; which one is open is view state (kept in `<project file>.view`, no undo step), while making, copying, renaming and removing one are edits. A clip plays a part of a file, another timeline (a nested timeline) or nothing (an adjustment layer): `project::ClipKind`. A timeline never plays itself, directly or through others. An adjustment layer's colour applies to the picture below it as a whole, in linear light: what is below is put together first and drawn again coloured.
- Saving: every change, undo and redo goes into the project's journal at once; the journal holds the whole session from a copy of the file as it was opened (`<file>.journal.start`), so recovery replays it onto that copy and comes back with the undo history too, whatever saves happened in between. Full saves (idle autosave and Ctrl+S alike) snapshot on the interface thread and write on a worker, one at a time per project, and an older snapshot never replaces a newer file. Every small file (project, settings, presets, labels, templates, layout, the updater's state files) is written whole or not at all with `diag::disk::write_atomic` (also `project::disk::write_atomic`; a temporary file of each write's own, then a rename; leftovers a day old are removed at start); files changed often from the interface go through a `project::disk::Keeper` (its own thread, one write at a time, newest last, failures reported), and settings are handed over only once the pointer is let go or they have settled.
- The files that belong to a project (journal and its start, set-aside journals, unfinished saves and writes of them, backups, thumbnail, timeline layout, saved versions) are listed in one place, `project::side_files`. Moving, renaming and deleting a project go by that list; a new kind of file kept beside projects is added there. Deleting moves files to the recycle bin and never touches recordings.
- Shortcuts can be changed (the keyboard shortcuts page), so the shortcut table holds the combinations in use and interface text asks it for key names (`keys_for`, `keys_or_name`, `tip`) instead of typing them; it writes them with the characters printed on the keyboard in use (the system's, followed live through `crates/os`, unless one is picked on the page). Settings keep only the changed ones, by key position and US key names. No two commands share a combination.
- Templates (reusable intros and outros) belong to the person, not to a project: each is a small file in `templates/` in the app's data folder with its own format version, and nothing about them is stored in a project file. Dropping one in is an ordinary edit that carries the whole template.
- Proxies belong to recordings, not projects: one per file in the app's cache folder, named by the file's fingerprint, shared by every project and dropped oldest-used first within the disk budget. They are not `project::side_files` and nothing about them is in a project file. The proxy mode (Off / On / Auto) is a setting. Export never reads proxies (its preview workers are never handed the shelf). Clearing the cache (Settings › Cache, for the open project or all) removes only proxy files from the cache folder, never recordings or project files; a proxy cleared on purpose is remembered in the cache folder and never built again by itself (Auto leaves it cleared), only when asked for: by hand ("Build proxy now", "Build proxies" for chosen files or the whole project), or by switching Proxies to On, which asks for a proxy for every video file and so builds the open project's cleared ones again. Proxies are built several at once on a processor with many cores, a long file in stretches side by side joined at the end (the same frames and times as one pass); "Build proxies at full speed" builds every missing one with more of the machine, also while the timeline plays, until none is left.
- Frames decoded on the window's graphics card are kept there (`engine::frames`), within a memory budget that is a setting (Settings › Playback & proxies › Memory for playback, `jobs::Budgets::card_frames_mb`; Auto is a quarter of the card's memory, 256 MB to 8 GB, followed live by the workers). The viewer reads ahead of the playhead into it, up to 10 s, while playing and while paused (`engine::preview::ahead`), so a stretch of heavy frames shorter than that never stalls the picture; while playing, frames behind the playhead make room first. Frames that make room on the card are read back into the computer's memory, within Settings › Resources › Memory for frames (`engine::preview::kept`), unless the window is drawing them; nothing about either is in a project file.
- Voice-overs are recorded into WAV files (32-bit float, mono, the microphone's channel chosen in Settings › Audio) in a folder beside the project, "<project> voice-overs" (`engine::record`: the microphone on a thread of its own, its callback filling a wait-free ring, nothing kept until the timeline rolls); they are recordings like any other, never removed with the project. A take is placed by one command, `PlaceRecording` (the file added and placed at the playhead where recording started, on the track asked for, the audio target or a "Voice-over" track; where that stretch is taken, on the first free track under it or a new one of the same name, so takes over the same stretch stack and are kept to choose from). Which microphone, its channel and the count-in are settings.
- A project's media labels, custom lists and notes are project data (`project::Library`, format 13), changed by undoable commands like any edit. The library's SQLite index (`crates/library`) is derived: built in memory from the project when it opens and kept in step on its own thread, never written back, never a file on disk. Labels are per project; label names and colours can also be offered in every project ("everywhere"): those belong to the person, like templates, in `labels.ron` in the app's data folder with its own format version (`project::global_labels`). Putting one on a file copies it into the project's own labels (an ordinary undoable edit), so a project file never depends on that file; taking one out of the set leaves every project that used it with its own copy.
- Importing on the Library page (Import media…, files dropped there, New in your folders) puts files in the project's media only; importing on the Edit page also puts each file at the end of the open timeline. Several files imported at once onto an automatic timeline settle it on the size and rate most of their videos share (pictures and videos under a second left out unless that is all), in the same undo step as the first file (`Command::ImportSettled`).
- While a dialog is up (`ui_kit::dialog`: modal, Escape or a click outside closes it, the click going no further) the shortcut table gives the page behind it no keys; while a text field has focus only Ctrl shortcuts fire. Names (a new label, list) are asked for in a small dialog of their own, never in a field inside a menu, which loses the keys when the menu closes.
- The Library page adds files with the ordinary commands: a whole file as `PlaceMedia` / `InsertMedia`, a part marked with in and out (or at a level chosen from its loudness) as a template made on the spot and dropped in with `InsertTemplate`, so it is one undo step on the tracks the whole file would take. Marks and the levels chosen per sound stream are kept for the session unless Settings › Library says to save them in the project (`project::MediaUse`, format 15, changed by `SetMediaUses`: one undo step per change); the file itself is never changed. I and O mark in and out on every page (the region on the Edit page).
- A media path in a project file is normally a full one; a relative path means "from the project file's folder" and is made full whenever a project is opened (`project::file::resolve_media_paths`). Packages (`project::package`: the project and only the media its timelines use, in one folder) are written that way so they open wherever the folder is moved. A package holds a clean save, the launcher's picture and the timeline layout, and the saved versions only when ticked (asked each time, off at first; then the files only they use go in too); never the journal, backups, templates or proxies. Saved versions' relative paths are from the project's folder too (`versions::load`).
- Export formats are listed once, in `media::encode::formats` (containers, picture and sound codecs, which go together, each codec's encoders in the order tried: the graphics card's, the system's, then the processor's); pages list them from there and ask `engine::export::Encoders` (on a worker) what this machine can encode. Every encoder aims at a bit rate from the quality, so the size shown before export holds whichever encoder opens. Pictures are 8-bit 4:2:0 BT.709 limited range for now, with a key frame at least every two seconds, each starting a closed group, and H.264 in its High profile: what video sites ask for.
- A file's sound is timed from its picture's start (`media::audio`; a file of sound alone from its own), so sound that starts before or after the picture keeps that offset, as players play it. Samples are counted, never taken from each packet's rounded timestamp, and a jump lands on the sample a straight read reaches; the mixer jumps only on a real jump (a cut, a seek, a change of speed), so played and exported sound is the file read straight.
- The Export page's own presets belong to the person, like templates: one small file, `export-presets.ron` in the app's data folder, with its own format version and codecs written by short names of their own; nothing about them is in a project file. How fast exports went on this machine is a setting (`export_pace`), used for the time the page says one will take. A queued export is the timeline as it was when it was added; the queue belongs to the window and runs on every page, one export at a time.
- An export at another shape than the timeline's fits the timeline's picture inside with plain black bars (never cut off or stretched); "1080p" in a preset means 1080 lines on the shorter side with the timeline's shape kept.
- Sound is mixed by `crates/audio` (pure Rust, no device): a fixed strip of every effect per track in the Audio page's order, 256-frame blocks at the device's rate, run in the sound card's callback with nothing allocated, freed, locked or waited on there (a test counts allocations). Numbers travel as small commands through a wait-free queue (heard within one block); what needs memory (a track, its lines, a learned noise profile) is built off the thread and swapped in, the old sent back to be freed elsewhere. Each track's sound comes from a ring a feeder fills; a dry ring plays silence and the feeder skips as much. Every track always passes the clean-up's delay and the mix the limiter's, so the delay is fixed and taken off the clock. Track effects, role, pan and volume and pan lines (timeline time) are project data (`project::TrackSound`, format 16; distortion, echo and reverb format 43, after the compressor), every effect off by default; the loudness meter and true-peak limiter live in `audio::dsp` (`engine::loudness` and `engine::limiter` re-export them). Playback and export both mix through it: a feeder per playback (`engine::feeder`) decodes each track's clips half a second ahead into its ring, the sound card's callback (`engine::output`, cpal's `realtime` priority) runs the mixer, and export runs the same feeder and mixer offline (`engine::offline`), so export equals playback to the sample; with every effect off the sound is exactly what it was before the effects came. A nested timeline sounds exactly as it does opened, its master included: the feeder of the track its clip is on mixes it with an `OfflineMix` of its own (`OfflineMix::nested`, its fixed delay mixed ahead and thrown away; made afresh on a real jump), at the rate that plays it at the clip's speed (with a ramp, at the outer rate and read as a ramped file is), then the clip's own sound and the outer track's strip apply. While playing, the editor hands the playback the project whenever the mix changed (`Playback::follow`, a comparison per frame), so track and master changes and their undo are heard within a block; jumps (`Playback::jump`) keep the sound card open.
- A stereo stream at default settings (clip, track and master at 0 dB, centred, every effect off) reaches the sound card as the file's own samples, left and right, to the bit; several streams are their sum, none turned down on import. Playback opens the card with a stereo stream whenever it mixes more channels and takes one, so the system is handed stereo, as from other programs, rather than the front pair of a 7.1 layout. Over full scale the card is handed full scale: no limiter is on by default, in playback or export (`docs/research/sound-quality.md`).
- Sync by sound (`engine::sync`) compares what clips play from their files and moves them with one edit (`LineUp`, one undo step; in the way of something, sound takes a free track and a picture is refused, as when a clip is dragged to another track): a clip with a picture moves by whole frames, sound alone lines up to the sample (edges on frames, its place in the file slipped by the rest). An unsure match moves nothing unless the person asks (Move anyway).
- A clip's own volume and pan lines (`project::ClipLines`, format 17) are kept at moments of its file, like look keyframes, so they stay on the sound through moves, trims and speed changes; a track's lines stay in timeline time. Lines are drawn on every timeline and edited with the lines tool (A); a change is one undo step.
- The Audio page's changes are ordinary undoable commands (`SetTrackSound`, `SetMasterSound`, `SetTrackMix`); a value being dragged is kept by the page and playback follows the project as it would be (`AudioPage::shown`), so it is heard while it moves and becomes one undo step when let go. Its bottom view (Timeline, Mixer, Split and Split's direction), the heights its parts were dragged to (`audio_heights`: shares of the page's height through `ui_kit::splitter::stack`, never in the project file) and how its loudness overview counts are settings, the same for every project; the Show filter is for the session. The loudness aimed for is one setting shared by the master column, Settings and the overview. Counting over several plays or inside the region tallies readings of the meters every 100 ms of the timeline (`audio::dsp::loudness::Tally`); "every play" shows the master meter's own count, as the Edit page does. Track meters have sample peaks only; true peak is the mix's. The band across the middle shows the clarity check or a live picture of the sound (Spectrum, Loudness, Tracks, Stereo; which one is a setting); its histories are kept by the page for the session only, never in the project. One analyser serves the EQ and the band (`audio::Listen`: a track, or the mix after the master); the EQ tool has it while open.
- The clarity check (`engine::clarity`) listens to each track as the mixer hears it (the audio crate's own strips, ducking keyed by dialogue) and never changes the sound; its fixes are ordinary undoable `SetTrackSound` edits on one track that change only the effect they name: ducking -10 dB under the dialogue (threshold 15 dB under its speaking level), a -3.5 dB cut at 300 Hz and a -2.5 dB dip at 2.5 kHz for the voice, both Q 1, put in a flat EQ band or deepening one already there. Another track covers the voice per band from 6 dB under it to 6 dB over it, weighted by the published Speech Intelligibility Index band importance; only dialogue-role tracks count as the voice, every other heard track can cover it; three tracks piling up between 200 and 500 Hz make a muddy zone. The master is left out of the check. On the Audio page it checks around the playhead (a second either side) once playback stops and the playhead and tracks have rested 400 ms, or the region when asked (Check the region); a check no longer wanted is cancelled; findings show on the shared timeline as coloured stretches (`ui_kit::TimelineSpan`, colours in `ui_kit::theme::clarity`).
- Closing a gap is the same everywhere: a ripple delete (Backspace, `RippleRemoveClips`), a selected gap closed (`CloseGap`) and a ripple trim move everything after the gap back on every track (every sync-locked one, and the track it happens on), so linked sound streams and layers stay in step; a clip on another track in the gap refuses it with the reason instead of being cut. The older same-track ripple of `RemoveClip` / `RemoveClips` stays only for old journals (commands keep their meaning).
- Linked clips (`Clip::link`: a picture and its sound streams) are selected, moved, trimmed and split together; `Unlink` sets every clip of a link on its own, sound streams apart from each other too. Settings › Editing › "Always unlink audio and video" is held by the open `Document` (`set_always_unlinked`): a change that would leave links is written to the journal as `Steps([change, UnlinkAll])`, one undo step, so replay gives the same project whatever the setting is then.
- Clips paste by the rule keyframes paste by ("places what fits and replaces clashes"): at the edit point, on the tracks of the same kind and number (missing ones made), cutting away what they land on there, nothing else moving; a nested clip that would play its own timeline is left out and counted. Copy copies the chosen keyframe marks when there are some, else the selected clips; Paste pastes whichever was copied last. Cut leaves the gap unless the "Cut closes the gap" setting is on.
- A picture's effects are an ordered list on its clip (`project::Effects`, format 19), whole millionths like a look, changed by `AddEffect` and `SetEffects` (one undo step each; a drag is one step when let go). The compositor draws a picture with effects upright and coloured at the size it takes in the frame, applies its effects one after another in linear light (`render::Effects`, two pictures taking turns), then places it, in preview and export alike. An effect's settings can change over the clip (format 24): keyframes per setting at moments of the clip's file, like a look's, worked out with the same whole-number steps. Effects that draw past a picture's edges (outline, drop shadow; format 35) make room around it as they need it, sizes kept those of the picture as it came (theirs are made the frame's by `engine::frame`, so a small facecam's outline is as thick as a large one's), and the compositor places the larger picture so the picture itself stays put (`render::Applied::grown`); an effect that makes part of a picture see-through (rounded corners, a chroma key) keeps it from hiding what is below. A chroma key compares colours as shown, against their brightness, never as light. Sound clips and adjustment layers have no effects yet; the Composition page (phase 11) will turn each list into a graph. A picture's blend mode (`project::BlendMode`, format 23) is a clip setting, not an effect: the compositor draws it with the graphics card's own blending, and any mode but Normal never hides what is below it.
- A transition (format 25) is kept on the clip coming in (`Clip::transition`, `project::transitions`) and plays centred on its cut with the clip ending where it starts on the same track, never longer than either; nothing is trimmed or overlapped for it. Each clip is read past its edge while its file goes on (at one speed; a ramped clip holds), else holds its edge frame. A transition whose clips no longer touch waits, unused; a split leaves it on the left part. Files only for now; the compositor draws the two pictures with their looks changed and, for some (whip pan, luma fade, glitch; format 42), passes added after their own effects (`engine::frame::transition`), so preview and export agree.
- A title (format 26) is a clip of its own (`ClipKind::Title`, no file, words and look in `Clip::title`, `project::titles`), added like an adjustment layer (the first free video track from where it is asked for up, or a new one on top). The engine lays its words out by its layout in the timeline's frame and draws them on the processor into only the part of the frame they cover (`engine::title`, the interface's own font made heavier), at the size that part takes on screen, kept while it stays the same; the compositor places that picture like any other, so a title's look, effects and keyframes work as a picture's and preview and export agree.
- A box that follows what it covers (blur and pixelate) is ordinary effect keyframes: `engine::track` follows it through the file on a thread of its own and the result is set as the box's Left and Top keyframes (`Effect::following`, one `SetEffects`); nothing about the following itself is kept. Stabilise works the same way (format 27): `engine::steady` analyses the clip on request and its result is the effect's view keyframes and zoom, drawn as a Move pass; no analysis is kept elsewhere.
- A picture's grade (format 28) is project data on its clip (`project::Grade`: layers of primary corrections and curves, each maybe kept to a colour range and a mask (format 30), whole millionths), set only by `SetGrades` (one undo step for one clip or many). The engine turns each layer that changes something into a `render::Effect::Grade` pass ahead of the clip's effects (`engine::frame::grade_numbers`), in linear light, so preview and export agree. The Color page grades the selected picture, else the top one under the playhead; a value being dragged is shown through `ColorPage::shown` and becomes one step when let go. Its scope reads the frame the preview put together, drawn small on the graphics card and read back on the preview's worker, only while the page shows (`Preview::set_scope`). Auto white balance (`engine::white_balance`) only ever writes the ordinary Temperature and Tint, when asked.
- Fades (format 32) are at a clip's ends, exact lengths on the timeline: a sound's in `Sound` (on a quarter sine), a picture's in `Clip::fades` (`project::fades::PictureFades`, straight, to see-through, applied to its opacity by `engine::frame`), each with a curve in millionths that bends it (the plain fade to the power 4^(-curve), `project::fades::level`, the one formula the mixer, the compositor and the timeline use). On the timeline they are changed by a handle in each top corner of a clip and a point halfway along each fade (`ui_kit` `timeline::fades`), one undo step when let go (`SetSound` for sound, `SetFades` for a picture); a split keeps the fade in left and the fade out right.
- A nested clip never changes length by itself when its timeline does: what lies past the end of its timeline is hatched on the clip, and "Fit to the nested timeline" in its menu trims it (one undo step).
- The status line fades out six seconds after its message last changed; undo and redo say what they undid or redid, and open the timeline they changed when another one is on screen.
- Tracks are named one way: "V1", "A2" (`Sequence::next_track_name`), whether added by hand or made by an import. An imported sound stream names its track only when its file gave it a title ("Mic", "Game"); the "Audio 2" made up for a stream without one is never a track's name (`project::tracks::name_for_stream`).
- A track's lock and colour (format 33) are project data, set by `SetTrackLocked` and `SetTrackColour` (one undo step each). A lock is checked once for every command, after it applies (`project::tracks::keep_locks`): anything that would change a locked track's clips, or remove the track, is refused with its name; its mix, sound, name, colour and place still change, and a locked track is never left out of what plays. Which audio tracks have a column beside the master column is view state (`TimelineView::columns`, `ui_kit::timeline::pins::Pins`: those pinned and those taken off, kept in the `.view` file, no undo step); whether every audio track gets one is a setting (Settings › Audio).
- A track's sync lock (format 34, `Track::unsynced`, set by `SetTrackSync`) is project data because edits depend on it: an edit that moves what comes after a point on other tracks (closing gaps, ripple trims, inserts, changes of speed) moves a track whose sync lock is off only when the edit is on it (`project::tracks::follows`); with every track sync-locked, as in every older project, edits work exactly as before, to the ids they give. Cutting the region out of the timeline still cuts every track. Target tracks are view state (`TimelineView::target_video` / `target_audio`, kept in the `.view` file): placing a file from the media drawer or the Library hands them to the command (`project::tracks::Targets` on `PlaceMedia`, `InsertMedia`, and `sound` on `LayMedia`), so the journal holds where it went; none, or a track that is gone, means the first of its kind.
- Without a sound output, or once it goes away while playing (the mix is taken back from its callback), playback still mixes the timeline at real-time pace on a thread of its own and throws the sound away (`engine::output::Paced`): the clock, meters, loudness counts and ducking work as with sound, and the master column and status line say "No sound output: meters still work".
- A recording of one channel is measured as one channel for loudness and true peak (`Loudness::mono`), as the loudness recommendation says, not as the two channels it is spread over to be played.
- Settings look and work the same in every program (`ui_kit::settings`): a large window under the top bar (not a page: it is reached from every page and from the launcher, and the page tabs stay about the work), the categories as tabs across its top (not a sidebar; in a second row when they don't fit in one, so every tab is in sight), a search box at the right end of the tabs, and the open tab's settings in titled cards, one row each: label and a line of description on the left, the control on the right in one column (a toggle for on and off, a segmented control for two or three choices, a dropdown for more, a slider with its value for numbers, Auto as a switch beside its number, a button for an action), a "Restart" badge where a change waits for the next start. A program lists its settings as data with ids; search and `open_at(id)` work on that list. Settings are still kept and written as before.
- The user guide lives in `docs/user-guide/` (one self-contained `index.html` and its `images/`), ships with every installer (each version's folder has `user-guide/`; the AppImage's `usr/share/user-guide/`) and is updated in the same commit as any feature it describes. Both programs open it in the system's browser from Settings › Help and with F1 (`ui_kit::user_guide`, `os::open_with_system`); its shortcut tables are made from the shortcut table and a test keeps them so. Screenshots come from `docs/user-guide/tools/shots.sh`.
- Waveforms belong to recordings, like proxies: read once, every sound stream of a file in the same pass, and kept on disk in the cache folder's `waveforms/` by the recording's fingerprint and stream (`cache::waveform::Store`, a budget of its own, used longest ago removed first; each stretch's loudest, highest and lowest sample, a file of an older version read again). How they are drawn (shape, colours, side, scale) is a setting. Clearing proxies leaves them; Settings › Cache clears them (with the clip pictures and loudness readings) on their own. Nothing about them is in a project file. Clip pictures of long recordings are the nearest key frames unless Settings › Editing › Clip pictures says Exact; they are kept the same way, in the cache folder's `pictures/` (small JPEGs, a budget of their own, cleared with the waveforms), with each file's Library card picture beside them, read first and on its own. The Library's loudness readings of a file belong to the recording too: every stream measured in one pass and kept in the cache folder's `loudness/` by fingerprint, a few bytes each, and cleared with the waveforms.
- FFmpeg is linked dynamically and its licence text ships with the app.
- The editor calls `diag::start(brand::VERSION)` first and `finish()` on a clean exit (logging, crash reports, crash detection); a helper program such as the launcher calls `diag::start_helper` instead (its own log files and crash reports, no crash detection). Crash detection is per process: each editor run keeps its own marker (`sessions/<process id>.running` in the data folder) and holds a lock beside it while it runs, and only a marker whose lock is free counts as a crash (even one with the new run's own id), so several editors (one per project) can run at once. The graphics start markers (Vulkan start, decoding on the window's device) are kept the same way, per process, with `diag::marker`.
- Releases are tagged `vX.Y.Z` (pushed, or typed into "Run workflow"); the release workflow builds, tests, signs and publishes. Pushes to `main` publish automatic betas (`brand::VERSION` comes from `BUILD_VERSION` then). Updates are trusted only with a valid signature from the `RELEASE_SIGNING_KEY` secret, kept in the `release` environment and used only by the signing job of runs on `main` and `v*` tags; pull request builds are never signed and skip the update drill. Every workflow's token only reads unless a job asks for more (only the release workflow's publishing job does, and never for a pull request), and actions are pinned by commit with the version in a comment.
- A release is only published after an installed copy of the previous one has updated to it by itself in the release workflow (the update drill, `RELEASING.md`). Anything that changes how updates are found, fetched, installed or started is covered by it; keep `launcher --update-step` working.
