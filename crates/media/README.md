# media

Reading and writing media files: a small, safe layer over FFmpeg. The rest of the app sees plain Rust types and explained errors; every FFmpeg call stays here (this crate is the FFmpeg wrapper where the working rules allow `unsafe`).

## Status

Phase 4A in progress: probing, fingerprints, frame timing, decoding to pictures and to sound, and writing proxies are done. Pictures come as the decoder's YUV planes for the GPU to convert, as images already on the window's graphics device (approach C in `docs/research/decoding.md`), or as RGBA. Encoding comes in Phase 6.

A jump searches by the file's picture stream (recordings often list jump points for the picture only, and searching by the sound then reads the whole file up to the target), lands a little early and drops up to the exact sample; where the file has no sound at the time asked for, silence comes first |
| `src/encode.rs` | `Writer`: writes an MP4 with H.264 pictures and AAC sound. The picture encoder is the first of `VIDEO_ENCODERS` that opens: the graphics cards' own, the system's, then the CPU's (or the CPU's straight away when asked). Pictures are tagged BT.709, limited range, with a key frame every two seconds. `finish` completes the file; dropped without it, the file is cut short |
| `src/decode.rs` | `VideoDecoder`: the frame on screen at a time (found by timestamp). `picture_at` gives it as the decoder's YUV planes (`Decoded::Yuv`) when the format is 8-bit 4:2:0 with a BT.601 or BT.709 matrix, else as RGBA; `frame_at` always gives RGBA, scaled to fit a size and turned upright, in the file's own colour matrix and range. GPU decoding (Direct3D 11 on Windows, VA-API on Linux; the decoder that supports the GPU is picked per codec, since for AV1 it isn't FFmpeg's default) with a CPU fallback per file; decodes onward for small steps and seeks for jumps. `open_on_device` opens a decoder on the window's own graphics device instead, or fails with the reason; `level()` says which of the three ways a decoder ended on (`Level`) `picture_at_while` and `frame_at_while` are the same for a request that may be overtaken: between frames they ask what is wanted by now and give the decode up, stop it early or finish it accordingly (`Newer`, `Reached`). Their `keep` is handed every frame decoded on the way, with the time the next one starts, by decoders that `keeps_frames()` (those on the window's device; `keep_every_kind` makes any decoder do it, as planes in memory). `key_frames()` is the container's list; `open_for_glances` (one thread, for single frames) and `key_frame_picture` (the key frame before a moment, at once: the first picture after a jump in a file without a proxy); `open_proxy` (a proxy: on the CPU, one thread, the original's frame times); `is_near` (a moment a few frames ahead, no jump: quicker decoded than stood in for); `decode_cost` (frames decoded in a row, timed, for judging whether a file needs a proxy); `last_work()` says where the last picture's time went (`Work`: the jump, the first frame out, the frames decoded). | `src/jump.rs` | `KeyFrames`: the key frames a container lists for a stream, and the rule for when a decoder jumps and when it decodes on: jump when going back, or when a key frame on the way saves at least a second of decoding (a jump is not free; `eager` for a proxy: any key frame on the way); a fixed distance where nothing is listed. `before` (the key frame before a moment) and `longest_gap` (the longest stretch to decode, to the end after the last) |
| `src/proxy.rs` | `write`: a proxy of a picture stream, an MP4 with H.264 whose shorter side is 540 pixels, a key frame every 8 frames and no frame depending on a later one, every frame with exactly the original's timestamp (in its time base, from its zero; each packet written once the next says how long it lasts, or the container leaves the last frame out), stored as the original is (not turned) with its colour matrix and range written down, no sound. | `src/vulkan.rs` | Decoding on the window's graphics device. `WindowDevice`: FFmpeg's device context built around the window's device (`video_device::VideoDevice`) instead of one FFmpeg creates, shared by every decoder that works this way. `GpuFrame` (`Decoded::Gpu`): a decoded picture as two images on the graphics card, with what the shader needs. ## Decoding on the window's device

Three ways to decode a file for the viewer, fastest first; `engine`'s preview tries them in this order per file:

1. **On the window's graphics device** (`open_on_device`): FFmpeg's Vulkan decoder for H.264, H.265 or AV1 (found by asking each decoder what it supports, as for the other GPU path), working on the device that draws the window. Only when the editor hands that device over, the device decodes the codec, and the picture is 8-bit with colour at half size. Nothing else will do here: if FFmpeg can't decode on the device, opening fails instead of quietly decoding on the CPU.
2. **On the GPU's video decoder with a copy back** (`Decoding::Best`).
3. **On the CPU** (`Decoding::Software`).

A picture decoded the first way stays on the graphics card. `picture_at` copies the picture's part of the decoder's image (without the padding decoders add, and from the crop's corner) into a pair of plain images there (`video_device::PlaneImages`), waits for the card to finish, and returns them as a `GpuFrame`; the decoder's own image goes straight back to its pool, so the pool can't run dry however long the viewer keeps a picture. The size asked for doesn't matter: nothing is copied to memory, so nothing is saved by halving.

The copy follows the rules FFmpeg's header sets for anyone who touches one of its frames, quoted in `src/vulkan.rs` where each is followed: the frame is locked just before the submission and unlocked right after it, without waiting; the submission waits for the frame's semaphore at the frame's value and signals the next value, which is written back; the layout the image is left in is written back too; and the queue is locked with FFmpeg's own lock for the moment of submitting. One thread decodes, as in the measurements.

Clip pictures, project pictures, saved frames, waveforms and export never use the first way.

## FFmpeg

- Linked dynamically through `ffmpeg-sys-next` (8.1). The build reads `FFMPEG_DIR`, which `.cargo/config.toml` sets to `.ffmpeg/sdk`; `cargo xtask ffmpeg` puts the build pinned in `packaging/ffmpeg.env` there (a GPL build; the app is GPL too).
- The installers ship the same build's shared libraries and licence text.
- Probing opens the file and reads its headers, which can take tens of milliseconds: call it from a worker, never the interface thread.
